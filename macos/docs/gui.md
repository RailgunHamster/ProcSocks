# macOS 菜单栏应用

界面使用 SwiftUI，菜单栏入口、弹出面板和窗口由 AppKit 管理；网络转发仍由
Rust 核心负责。无需额外 GUI 依赖，支持 macOS 13 及以上版本。

## 构建与使用

需要 Rust 和 Xcode 的 Swift 工具链。在仓库的 `macos` 目录运行：

```sh
scripts/build-macos-app.sh
open dist/ProcSocks.app
```

点击菜单栏的分流箭头图标打开面板，也可以重新打开应用进入设置。
图标与应用图标使用相同的分流箭头，在菜单栏自动适配浅色和深色外观。
设置窗口的 ProcSocks 菜单中有“打开菜单栏面板”（⌘⇧P）。
首次显示时放在靠近系统控制项的右侧区域，避免默认位置落在 MacBook 刘海下。
之后会记住你按住 Command 拖动选择的位置。

1. 在“代理服务器”填写已有 SOCKS5 的主机、端口和可选认证信息。
2. 在“应用与进程”勾选应用，或切换“全部进程”选择具体可执行文件。
3. 点击“启用代理”，在 macOS 自己的管理员认证窗口完成认证。

应用选择匹配应用包内的全部可执行文件，包括包内辅助进程；独立可执行文件
选择只匹配该完整路径。应用包外的共享系统辅助进程需要另选。
可以提前选择尚未运行的应用，或通过“添加…”选择文件。

“高级规则”中的代理正则与列表选择合并，绕过规则优先。复杂的旧正则会保留
在高级规则中；已有普通路径规则导入后保留其原始匹配语义。
保存前会调用 Rust 核心验证正则和真实 pf 语法。运行时保存会重新启动后台
核心应用新规则；仅修改勾选但尚未保存，不会改变正在运行的规则。

“开机时启用代理”控制 root 后台服务；“登录时打开菜单栏应用”只控制 GUI。
停止代理不会取消已保存的开机启用选项。退出时若后台仍在运行，可选择停止
后退出或仅退出界面。

## 实时流量

打开“实时流量”查看按进程列出的下载/上传速度、累计下载/上传量；点击某个
进程即可查看它的速度曲线，也可返回合计图表。支持最近 5、15、30 分钟范围，
按名称或 PID 搜索，以及仅显示列表中已选择的应用（包含包内辅助进程）。
菜单栏面板也显示当前上传和下载速度。

统计来自 Rust 代理核心的实际转发计数，每秒更新。仅包含命中代理规则并经
上游 SOCKS5 隧道转发的 TCP 字节，包含 TLS 加密数据；不包含直连回退、
UDP/QUIC、SOCKS 握手、TCP/IP 包头或重传。这不是运营商计费统计。
同一进程同时发起直连和代理连接时，只累计代理连接；高级规则命中的进程
也自动出现，无需再次在列表勾选。列表筛选只影响显示。

累计用量从打开 GUI、点击“重置统计”或后台重启后开始。统计基于成功写入
隧道/应用的字节，长连接未关闭时也持续更新；失败且未转发的字节不会计入。
代理停止或统计超过 5 秒未更新时，当前速度归零，历史曲线和累计用量保留。
图表保留最近 30 分钟，未选择其他范围时默认显示 5 分钟。

后台快照位于 `/Library/Application Support/ProcSocks/traffic.json`，父目录由
root 管理，文件仅可由安装后台时授权的 GUI 用户与 root 读取，每秒原子替换。
GUI 不再运行 `nettop`，也不读取其他软件的直连流量。升级旧后台后才能启用
此统计；界面提供“更新代理后台”，通过已有系统管理员认证流程应用配置。

macOS 的 pf 后端先截取配置范围内的非 root TCP 连接，再判断进程规则。
未命中的连接经核心直连回退，不送给上游代理，因此不计入代理流量图表。

## 配置与权限

首次运行在仓库构建目录中会导入 `procsocks.local.json`，原文件保持不变；
其他位置首次运行会使用不含凭据的示例配置。可使用配置菜单导入/导出 JSON。

GUI 配置保存到 `~/Library/Application Support/ProcSocks/procsocks.json`，目录
权限为 700，文件为 600。`_menuBar` 保存选择列表元数据，核心忽略该字段。
“最终生效配置”预览会隐藏密码。

管理员认证由系统完成；GUI 不读取或保存管理员密码。安装后的后台可执行
文件和配置位于 root 所有的 `/Library/Application Support/ProcSocks`，服务标签
为 `com.procsocks.menubar.core`，与 CLI 服务 `com.procsocks.agent` 分开。
连接日志是该目录下的 `core.log`，普通用户可以在 GUI 中查看。

## 独立原生网络测试

```sh
scripts/build-network-test-app.sh
open "dist/ProcSocks Network Test.app"
```

在 ProcSocks 的列表中勾选 **ProcSocks Network Test** 后启用代理，点击测试
App 的“运行 HTTPS 测试”。它对 Example、Apple 和 ChatGPT 的公开地址执行：

- Network.framework 的直接 TCP/TLS 请求，优先绕过显式代理。必须同时在
  ProcSocks 日志中看到测试 App 的 PID、`decision="proxy"` 和还原后的目标域名，
  才能证明经过了透明代理。
- URLSession 请求，保留本机已有系统代理设置，用于比较原生 HTTP/2 的表现。

测试显示 HTTP 状态、字节数、耗时和是否使用显式代理；不关闭证书校验，
不携带登录凭据，也不更改系统代理设置。403/404 表示已收到网站响应，不能
证明登录后的 ChatGPT 功能可用；它们与超时、TLS 失败需要区分。
测试按照 Content-Length/chunked 消息边界完成，不必等待服务器关闭 TLS；
不完整的响应仍会报告失败。未取得显式代理指标时显示“未知”。

绕过规则对完整路径进行搜索。旧配置中的裸 `procsocks` 也会匹配项目目录
`procsocks-mac` 中的测试 App；需要测试透明路径时，将测试配置的该规则改为
`(^|/)procsocks$`，并确认日志中的决定确实为 `proxy`。新示例配置使用此精确
规则；导入的用户自定义规则不会被自动修改。

自动化可直接执行测试 App 的二进制并传入 `--report /absolute/path/result.json`，
它写入 JSON 后退出。请以普通用户运行；root 会被 pf 豁免。

“测试上游”只验证 SOCKS5 握手和 CONNECT 许可。部分上游会提前确认 CONNECT，
因此还需要上述完整 TLS/HTTP 测试判断实际联网是否成功。

## 重定向范围

pf 的 `rdr` 规则仅作用于 `lo0`。普通用户发起的连接先由 `route-to` 送入
`lo0`，再做目标地址改写；外部接口收到的回复保持原目的地址。
这尤其影响 `redirectPorts: "all"`：如果 `rdr` 没有限制接口，它会误改写
返回给上游代理/root 出站连接的临时端口，导致整条代理链路失败。
IPv4、IPv6 使用相同的接口限制。
